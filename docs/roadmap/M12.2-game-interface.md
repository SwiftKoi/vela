# M12.2 — The game's own interface

**Goal.** Vela ships the interface every game has: **a menu system and a settings system**, as Vela's
own, and a project can override any part of it.

**Depends on.** M12.1 (a project's screens must be expressible before an interface can be built from
them), M08 (save/load slots), M07.

**Crates.** `vela-world` (the settings store and its lifetime), `vela-replay` (persistence for it, and
the save/load screens' data), `vela-vm` (what a restore is told), `vela-ui` (the screens, the
`preference` dispatch, the settings vocabulary), `vela-cli` (the player), `vela-migrate` (the report
entries for `screens.rpy`'s app screens).

**Followed by.** M12.3 (media, input and language), then M13.

## Why this is its own step

`M12.1-screen-language.md §7` found that **fourteen of `the_question`'s 23 screens are not screens in
any interesting sense** — they are the interface to a *system*: settings, save files, history, help,
notifications. Migrating a screen language and providing an engine's interface are different jobs with
different evidence, and doing them under one milestone is how "implement what Ren'Py has" becomes
unbounded.

Ren'Py's answer has two halves, and the survey is explicit that we are copying the second and not the
first:

- **The look** — 48 skin images and 190 styles reading 126 `gui.*` values (`M12.1 §2`). **Not
  reproduced.** A migrated project inherits Vela's look, as a port does.
- **The systems** — a main menu, a game menu, settings with a store behind them, save/load with
  slots and pages, history, help, notify. **These we want**, because a game written in Vela wants
  them for the same reason `the_question` has them.

> **Decided: a default interface, and a project overrides any part of it.** Ren'Py's model, without
> its look. Vela ships a working menu, settings, save/load, history and help interface; a project that
> declares a screen of the same name takes it over and the rest keep working. This is what makes the
> milestone worth having — a project gets a usable game before it writes a screen — and it is why the
> exit criteria below are about *behaviour* (a setting persists, a slot loads, an override holds)
> rather than about how the default looks. §7's cut stands: the systems are ours, the skin is not.

## What exists, and what the systems behind these screens need

| Need | Exists | Missing |
| --- | --- | --- |
| A screen stack over the story | `open_screen`/`close_screen`, the presenter's stack, `Escape`, `advance` (`SCREENS.md §2`) | Which screens a *game* has, and how one is opened with arguments |
| Save/load | Slots, atomic writes, checksum, rollback (`M08`, `RUNTIME.md §5`) | The screen over them: pages, timestamps, thumbnails, delete, autosave/quick slots |
| Settings | **Nothing** | A store, its persistence, and the distinction from `World` state — a setting is the *player's*, not the save's |
| History | Rollback snapshots (`M08`) | A log of what was said, which is what a history screen and `nvl` both read |
| HUD | Nothing | Transient state for notify and the skip indicator |
| Help | `SCREENS.md §11` has the model | The input map itself (**M12.3**) and the screens that display it |
| Dialogue box, choices | The presenter draws a built-in box; `dialogue`/`pause` are overridable screens | `choices`, `input`, `quick_menu`, `confirm`, and every one of them overridable |

## Work items

1. **The settings store**, inside `World` and *outside the save*: a preference survives a load, is
   shared by every slot, and is not part of the world a replay reproduces. `World` gains a second
   lifetime beside the save schema — versioned the same way, migrated the same way, excluded from
   snapshots and rollback. (`M14-hardening.md` lists this as a gap; it is the first thing here.)
2. **Persistence for it**, versioned like the save schema, with the same rule: a missing migration is
   an error that names the gap (`E7201`).
3. **The menu system**: the screens a game has, how one opens with arguments, and the override point.
4. **Settings screens** over the store: text speed, auto-forward, skip behaviour, volumes (which wait
   on M12.3's audio), display mode.
5. **Save/load screens** over M08's slots: pages, timestamps, a thumbnail, delete, quick and
   auto slots.
6. **The dialogue log and its screen**, shared with `nvl`.
7. **Notify and the skip indicator** — the transient HUD.
8. **`confirm`**, and dialogue parity: `say`, `choice`, `input`, `quick_menu` all expressible as
   overridable screens rather than as presenter behaviour.
9. **About and help**, with the key list from M12.3.
10. **Migration**: `screens.rpy`'s app screens become report entries that name *this* milestone —
    "Vela has its own" — with a project's *data* (theme values) still honoured.

## Exit criteria

- [ ] A new project gets a working interface without writing one: start, load, settings, about, quit;
      save, load, settings, history, main menu.
- [ ] Overriding one of those screens in the project replaces it and leaves the others working —
      asserted by migrating a project that overrides exactly one.
- [ ] Any of those screens can be overridden by the project, and the rest still work.
- [x] A setting changed in one session is still set in the next, and is not in the save file.
      Evidence, in its three steps: `crates/vela-ui/tests/settings.rs` asserts the action-to-store write
      (a value, and a toggle flipping from its declaration), `crates/vela-cli/src/tests/ui_tests.rs`
      asserts the session's two halves — the write a player's screen makes and the read a later session
      does — and `crates/vela-replay/tests/preferences.rs` asserts that no save and no snapshot carries
      one.
- [ ] The save screen lists real slots with real timestamps, and loading one returns to the right
      place — asserted end to end, not by hand.
- [ ] `vela migrate` reports every app screen in `screens.rpy` as "Vela has its own", never as
      "unsupported".

## Status

**In progress — items 1 and 2 landed, and the vocabulary item 4 needs with them.** `World` carries a
`Preferences` store beside the save schema, and the rules that make it the player's rather than the
playthrough's are enforced where they could be broken: the serializer skips it (a save never carries
one), `World::snapshot` leaves it empty (a rollback never restores one), and `Session::restore` is
*given* the settings of the player it resumes for. Item 2 is the file: `settings.velaprefs` beside a
player's saves, the same envelope as a save without the schema digest, versioned with a chain whose gap
is `E7201` naming the step — and `vela run` reads it at startup, which is the one moment those settings
exist nowhere else. On top of that: `vela-ui::settings` is the vocabulary a screen writes, the checker
holds a written name to it (`E5020`) and a literal value to the setting's type (`E5021`), `vela doc
settings` emits the list, and `vela migrate` translates the sample's twelve `Preference(…)` uses onto
it — five to `toggle_preference`, two to `display_mode`, and the audio ones reported by name as M12.3's.
And a setting can now *change*: `vela_ui::settings::write` is the one place the two actions are carried
out, the windowed player uses it and rewrites the file at once, and the test runner uses it against the
run's own world — so a settings button is one a test can press. **Reading one is a question**, the way
`variant` is: `setting("text_speed")` is a value a screen draws (`bar value = setting("text_speed")`), a
condition it decides with, or a text, and it answers its *declaration* until somebody chooses. What is
**not** here yet is the engine *obeying* one — nothing types dialogue at a text speed yet, and the
registry's `read: false` is what says so — and the screens themselves, which are items 3–9.

**Item 3 is done: a screen is *called*, checked, and the interface Vela ships is real.** `open_screen(detail,
"Chapter one", 7)` passes values in the opened screen's parameter order and a parameter the call omits
keeps its default — §2.1's calling convention, with the values already resolved because a runtime carries
values rather than the syntax that wrote them; an argument *name* from a runtime is what an action cannot
carry, so a call from one is positional, and the reference says so. The registry states a *floor* for that
one entry (`open_screen(screen, …)`) instead of letting every action take any number of arguments, and the
two ways a screen is called now share one binding rule — including the host answers, which is where a real
defect was hiding (see below). An `open_screen` target is held to the screens the *game* declares, and its
arguments to the target's parameters (`E5009`/`E5010`), so a misspelled name is a diagnostic rather than a
button that checks clean and does nothing. And the interface exists: `vela_ui::interface` is one module of
Vela's own source with `game_menu(title)` in it, a project module can `use` it, and a project's own
declaration of the name is the one found.

> **Decided and landed, while building it: how an override is written** (the survey's open question). Two halves, and
> the first is what the resolution rule says: **a name resolves to the project first, and the interface is
> the fallback** — one line in `compose::find`, which is the one place the checker, the instantiator, the
> dependency walk, and the accessibility walk all arrive, so a project can both *use* the interface's
> screens and *replace* them with no second table anywhere (`SCREENS.md §2.1`, §2.7). The second half is
> what an override is **not**: it replaces a *name*, not a binding, so a screen the interface uses
> internally keeps using its own — otherwise an interface screen would draw differently depending on what
> the project happened to declare, which is exactly the coupling §2.1's "a screen is a pure function of its
> arguments" rules out. The look follows the same reasoning: an interface screen names `theme.*` tokens and
> never a `style`, because a style resolves in the declaring module (§5) and a project's styles are the
> project's. **The palette is the project's** — the interface's set is laid out with the project's colours
> over its own — which is item 10's "a project's data is honoured"; that injection is the one piece of this
> decision's last piece landed with the frame: the interface's set is laid out with the game's palette
> over Vela's, token by token, so `bg`/`fg`/`accent` in a project's theme are the frame's colours.

## Found during implementation

- **A `use`d screen's styles resolve in the *caller's* module, which decided what an interface screen may
  name.** `SCREENS.md §5` says a screen is compiled against the styles in its own module and that a
  cross-module reference is not seen yet, and the instantiation agrees: expanding a `use` happens inside
  the caller's context, so the used screen's `style` names would be looked up in the *caller's* table. That
  is invisible while a `use` stays in one file (both directions are the same module) and becomes the whole
  question the moment a project can `use` an interface screen: Vela's `game_menu` naming a style would draw
  with whatever the *project* declares under that name, or with nothing. So the rule for the interface is
  stated where a reader will meet it — widget defaults and its own `theme.*` tokens, never a `style` — and
  §2.7 says why. It is the same shape as the settings work's "a name is written as a string": a boundary
  the *feature* found rather than one the design predicted.
- **The one screen question that is not per file.** `use` resolves in the declaring file, so every screen
  check so far has been handed that file's declarations — but an `open_screen` names a screen the
  *project* has, and in the sample `navigation` opens `preferences`, `save`, `load`, and `about`, each
  declared elsewhere in `screens.rpy`. So the target check is a project-wide pass (`vela-ui`'s
  `check_open_screens`, asked by `vela-lsp`'s project answer, which is what both `vela check` and the
  editor read) — the second thing after the save schema that only the layer with every file can do. What
  it buys is the failure this milestone keeps producing: `open_screen("preferences")` with the name
  misspelled was a button that checked clean and did nothing. The boundary it draws is `E2001`'s: a bare
  word in that position is an *expression*, so the check reads the **string** spelling and stays quiet
  about a bare one — one mistake, one diagnostic — and a bare name that is a screen in *another file* is
  the false positive recorded in **Still open** below.
- **An `open_screen` *calls* the screen it opens, and the two ways a screen is called had to be one rule.**
  `use` bound its arguments in the callee's parameter order and filled the rest from their defaults; a
  runtime's call binds the same way, but its arguments are already *values* — an action carries values and
  no argument names, so a call from a runtime is positional, and the registry says so with a `rest` on the
  one entry that needs it rather than by letting any action take any number of arguments. What the two
  paths also had to agree about turned out to be a bug: `use` built the callee's scope from nothing, so a
  `use`d screen answered `setting(…)` with the *declaration* while the screen around it answered with what
  the player chose. Fixed by seeding the callee's scope with the caller's host answers, pinned by
  `vela-ui/tests/settings.rs`'s `a_used_screen_answers_the_store_its_caller_had` — which draws `0` instead
  of `45` without the fix, so it is the kind of thing a settings screen written out of `use`d panels would
  have shown and nobody could explain.
- **The sample's settings screen is twelve `Preference(...)` uses, and it already *looks* migrated.**
  Measured by value in `screens.rpy`: `text speed`, `auto-forward time`, `auto-forward`, `skip`,
  `after choices`, `transitions`, `music`/`sound`/`voice volume`, `all mute`, `display · window` and
  `display · fullscreen` — nine distinct settings — and `options.rpy` declares two more, as
  `preferences.text_cps` and `preferences.afm_time`. Every one of them is a `Word` to the migration and
  a `Word` to the checker, so the screen migrates, checks clean and does nothing: the *buttons* write
  `preference("display", "window")` and the `preference` action is `dispatched: false` — item 4's work.
  That is the failure this project exists to catch, and it makes the vocabulary a *checker* item as
  much as a screens one: those names want a closed set the way `key`'s semantic actions and
  `variant`'s have one.
- **Measuring that screen turned up two defects in the migration, and both are fixed** (in their own
  commit, before this item's next one):
  - **A comment at column zero ended a screen.** Ren'Py drops comment-only lines before it looks at
    indentation, and its own region marker — `#begin language_picker`, written flush left *inside* the
    sample's `preferences` screen — was read as structure instead. Everything after it fell out of the
    declaration and was dropped **in silence** (a line inside no declaration is nobody's to report), so
    the screen lost its language picker, a spacer and all five sliders. The reader treats a comment as
    trivia for indentation now, and the lines the fix restored are dispositioned like any others; the
    hole the silence came through is recorded in `M12-migration.md`'s **Still open**.
  - **A call in a *value* prop was lowered as an action.** `value Preference("text speed")` is Ren'Py's
    **Value** object — a reader and a writer bound to a setting — and not its action of the same name.
    Lowered as one it wrote `preference("text speed")`, one argument to an action the registry says
    takes two, and the restored lines made the migrated project fail `vela check` with five `E5013`s.
    It is reported now, and the bar goes with it: a bar with no value says nothing, and a widget bound
    to a setting is this milestone's settings screens.
- **The vocabulary is Vela's own names** (asked, not assumed): `text_speed`, `auto_forward_time`,
  `skip_unseen`, `after_choices`, `transitions`, `display_mode`, `music_volume`… in a closed set the
  checker holds to and `vela doc` can emit, with the migrator mapping Ren'Py's strings onto them — the
  shape `ShowMenu` → `open_screen` already has. Ren'Py's variable names (`text_cps`, `afm_time`) were
  rejected for putting a foreign engine's abbreviations into this language's surface, and its UI strings
  (`"text speed"`) for a vocabulary that is a string — which `style_prefix` and `variant` have each
  already refused.
- **The read is a question, and that is `variant`'s shape rather than a new mechanism.** A settings screen
  has to draw what the player chose, and a screen decides from what it has *plus what the host says*
  (`SCREENS.md §2.6`) — so `setting("text_speed")` is the second question: a **value** rather than an
  action (`bar value = setting("text_speed")`, `if setting("skip_unseen")`, `text setting("…")`), held to
  the same vocabulary (`E5020`), answering its **declaration** until somebody chooses, which is what makes
  a screen draw what the engine would do. The store travels in the scope a screen is laid out in, the way
  the variants do — which is what makes the answer the same in an arm, a loop body and a `use` argument —
  and a press that changes one re-lays the stack, so the next click reads what the press wrote
  (`vela-test`'s `a_screen_draws_a_setting_and_a_press_changes_what_it_draws`).
- **A settings screen marks its own current choice, because a control knows what it writes.** Ren'Py's
  radio and checkbox styles draw the current option through the *action* (`get_selected()`), and that is
  what makes `style_prefix radio` migrate honestly rather than as a style with no state to draw: `selected`
  now means *focused* **or** *the control whose setting is what the store holds* (`SCREENS.md §5.1`), asked
  at instantiation because that is the one place the action and the scope are both in hand, and stored on
  the node because a focus cursor moves without a re-lay and a setting does not. An unchosen setting is its
  declaration, so the default option is the one that starts marked — and the migrated `preferences` screen
  needed no migration change at all, which is the sign the read path was the missing half rather than the
  translator.
- **A toggle became an action, and the value word it replaced is why.** Ren'Py spells a flip as the
  value `"toggle"` (`Preference("skip", "toggle")`), and copying that would have put a second vocabulary
  inside an argument that only the runtime could check — so a typo would be a checkbox that silently
  does nothing, which is the failure this item exists to remove. `toggle_preference(name)` is the
  registry-shaped answer: one word, checked like every other action (`E5012`), with its setting held to
  the vocabulary (`E5020`) and the setting's *type* held to `bool` (`E5021`). Measured first: five of
  the sample's twelve uses are toggles, so it is the common case rather than an edge one.
- **A setting's name is checked; its value only when it is a literal.** A bare name in either position
  means two things — a *word* the screen writes, or an expression it computes — and only the screen's
  own scope tells them apart, which is why the checker now carries one (`check/screen.rs`'s `Scope`:
  variables and parameters, together for this question, apart for `E5017`'s, where a parameter is not
  writable). A value that is an expression is left to the runtime on purpose: reading
  `preference(text_speed, other)` as the word `other` would report a correct screen, and a check that
  fails a right program is worse than one that stays quiet. A choice is therefore written as a string,
  which is the spelling the migration emits.
- **A store with no vocabulary, deliberately.** The names are the interface's (`SCREENS.md §7`'s
  action and the screens over it), so `Preferences` is a name→value store that will hold a setting
  this build has never met rather than drop it as unknown — which is also what a settings *file* needs,
  since a file written by a newer build is read by an older one. The consequence is stated in
  `RUNTIME.md §2.1`'s **Not yet.** rather than implied: any name can be set today, and the check that
  a name exists arrives with the screens that write one.
- **The lifetime needed a third place, and it is the resume's signature.** The two obvious ones are
  the serializer (a save) and the snapshot (a rollback); the third is a *load*: `Session::restore`
  built its world from the snapshot, which now carries no settings, so a resumed session would have
  greeted the player with defaults. Taking them as an argument rather than exposing a setter is what
  makes it impossible to resume without deciding whose settings the session gets — the compiler asks
  at every call site, and each of the three that exist (a load, a rollback, and the tests) answers
  with a sentence about who the player is.

## Still open

- **Whether an override can be removed** as well as replaced — a project that wants the default back
  without deleting its own file.
- **A bare screen name from another file is `E2001` today.** Measured with the probe project: with
  `screen detail(…)` in `detail.vela`, `action open_screen(detail, …)` in `main.vela` is reported as
  *undefined name `detail`* — a right program failed, which is the one outcome the checker treats as
  worse than staying quiet. The string spelling works (`open_screen("detail", …)`, which is what the
  migration emits and what `SCREENS.md §2` now states), so this is a wart rather than a hole, and the fix
  is name resolution knowing that an `open_screen` argument is another vocabulary's: a `Target`-aware walk,
  which is a language-surface question because the walk sits in `vela-hir` and the prop *types* sit in
  `vela-ui`.
- **Whether `quick_menu` belongs here** or is presentation (M6/M7): it is a small overlay and it
  overlaps the presenter's own drawing.
- **How the settings screen is generated** from the store, or written: a setting that exists with no
  widget on the screen is the kind of drift a generated screen prevents.

## Risks

This is the milestone most likely to grow a house style nobody asked for. The mitigation is the cut in
§2: **mechanisms and systems are ours, the look is the project's** — and the exit criteria are written
about behaviour (a setting persists, a slot loads) rather than about screens looking right.
