# M12.1 — Screen language parity

**Goal.** Vela can express the screens a project writes: composition, state, scrolling, and actions
that are values. This is the first of the three steps that close the gap between a Ren'Py project and
a Vela one — **M12.1** the screen language, **M12.2** the game's own interface, **M12.3** media,
input and language — and §1–§3 are the survey all three work from.

**The survey's own goal.** `the_question` migrated *properly* — every file in it given a disposition
on purpose, and every piece of engine functionality that disposition turns out to need, named before
it is built.

M12 built the migration path and proved it on the story. The story was never the whole project: it
is 252 lines of a 2,522-line project, and the other 2,270 lines are screens, theme, engine config and
a translation tree. This milestone exists because migrating those raises a different question from
migrating a script. A script is *translated*. A screen language is *implemented* — Ren'Py's screens
are written against functionality Vela does not have, and how much of it to grow is a decision about
this engine, not about Ren'Py.

So this document is the decision, made up front and from the whole project, so the work that follows
is a checklist rather than a series of surprises.

**Depends on.** M12 (the migration path), M6/M7 (presentation, screens).

**Followed by.** M12.2 (the game's own interface), M12.3 (media, input and language). Both are named
in §7 and are *not* this milestone's work — the host systems a game needs are not the screen
language a project writes, and this document exists so the two are not confused.

**Crates.** `vela-ui`, `vela-text`, `vela-render`, `vela-migrate`, `vela-cli`, and the host.

## 2. The disposition rule

Every construct gets exactly one of three dispositions. The rule is the milestone.

**A. Translate.** The construct has a Vela equivalent that already exists. The migrator emits it and
the migration is *mechanical* — no engine change, and a bug here is a migration bug.

**B. Implement.** The construct is *functionality Vela lacks*. Ren'Py can express it and Vela cannot,
which means a migration can only report it — until the functionality exists. These are engine work
items, and this milestone owns them: the migration is the reason they are being built, and their
worth is not limited to migrations (a scrolling viewport, state styling and screen composition are
things a game written in Vela wants too).

**C. Report, and never migrate.** The construct is Ren'Py's own: compiled output, engine
configuration with no Vela counterpart, the API surface of Ren'Py's Python, or the *look* of Ren'Py's
default GUI. Copying these would be porting Ren'Py rather than migrating a project.

The line between B and C is the one that matters, and it is drawn by asking *is this the engine's job
or the project's?* A viewport is the engine's job — any project may want one. `gui.button_borders` is
the project's — it is a description of a particular skin, and Vela's answer is a theme of its own.

> **Decided, and the reason this milestone exists.** Vela does **not** reproduce Ren'Py's default
> GUI. The 48 skin images and the 190 styles that read `gui.*` values describe one specific skin;
> Vela draws its own dialogue box, `pause` screen and menus, and a migrated project inherits *that*
> look, the way a port to a different engine does. What Vela does acquire is the **elasticity**:
> the screen-language features those screens are written with, so that a project's *own* screens
> — the ones a person writes — migrate instead of being reported.

## 4. The screen language

What a Vela screen body can be written with, today, in full:

```
screen_line = "layer" IDENT | "default" IDENT "=" expr
            | "if" expr ":" block { "elif" expr ":" block } [ "else" ":" block ]
            | "for" IDENT "in" expr ":" block
            | "use" IDENT [ "(" args ")" ] [ ":" block ] | "transclude"
            | widget
widget      = IDENT { arg } [ ":" block ]
```

Seven forms, because items 2–4, 8–10 and 13 landed: a widget tree with a conditional, a loop and `use`
in it, a `transclude`, a `layer` line, and a variable. A variable is what serves as this language's
local; what is still missing is an *assignment* — one can be declared, and written by an action, but not
computed into mid-body — and the interactive props, which are M12.3's. That is the rest of the gap, and
it is why `screens.rpy` still reports rather than migrates.

A conditional's arms are **clauses of one line**, not lines beside it — `if`/`elif`/`else` are one
`ScreenLine::If` holding `elifs` and an `else_body`, exactly as `IfStmt` holds them for statements
(`LANGUAGE.md §3`). That is the whole reason the arms are not a `match` a walk can get half right: a
stray `else` is not something the grammar can produce, and choosing an arm is one decision
(`arm_of`) rather than a walk that remembers what the line before it concluded.

Counts are **screen-body occurrences** — a line inside a `screen` — not occurrences in the file. The
distinction matters and is measured: `style_prefix` is 20 either way, while `use` is 24 by a text
search and 14 as statements, and `viewport` is 11 by a text search and **1** as a widget (see §5.1).

| --- | --- | --- | --- |

Every arm is a conditional, and the migrator cannot lower this one away: `if a:` / `if not a and b:` needs `and`, which the screen evaluator does not have, and nesting `else: if b:` needs the `else` this row is about. The shape is the statement form's (`LANGUAGE.md §3`). |
| `use other_screen(args)` | 14 | **Implemented (M12.1)** — `use name[(args)]`, resolved in this file | **B**: composition. The largest single gap; every app screen is built from `use navigation`, `use file_slots`, `use game_menu`. |
| `style_prefix "say"` | **20** | **Implemented (M12.1)** — `style_prefix say`, resolved per widget | **B**: a prefix on a screen, resolved per widget (`say_window`, `say_text`), collapsing to the node's own `style` when written. Vela writes the prefix as a name rather than Ren'Py's string (`SCREENS.md §5.2`). |
| `for x in seq:` | **6** | **Implemented (M12.1)** — `for name in expr:` (`SCREENS.md §2.4`), with a list value and record fields | **B**: children from data. ### 5.2 Properties

~50 distinct property words, and the shape of the gap is consistent: **Ren'Py positions by fraction,
Vela positions by named anchor.** Ren'Py's GUI is built on `xalign 0.5`, `xpos 268`, `xanchor 1.0`;
Vela has nine anchors and `SCREENS.md §4.2`'s design rule — *if a layout needs arithmetic on pixels,
the layout system is missing a prop*. A migration therefore cannot translate a coordinate, and the
question is whether Vela should be able to express one.

Counts are `screen / style` — occurrences in a **screen body** and in a **`style` block** — because
those are two different questions: the first is what the screen language must express, the second is
what the theme (item 15) has to carry. A third kind is neither and is called out where it matters.

**How these were taken, and why the first pass was wrong.** Walk `screens.rpy` line by line and record
which *top-level* declaration each live line sits under — `screen`, `style`, or neither — by
indentation; then count a construct only in the bucket it lands in. Comments, string values, and prose
are excluded by construction, which is the whole difference. (The classification is textual, not a
parse, so a construct named inside an expression would still be counted — none of the rows here turns
on that.) The first pass instead counted occurrences as a text search finds them, which is right for
"how much of this file is about X" and wrong for "how much of a screen body depends on X"; it was also
inconsistent, because the widget counts in §5.1 were taken line-wise and came out **exactly right**
(`textbutton` 57, `text` 55, `hbox`+`vbox` 57, `label` 37, `null` 6, `grid` 1, `frame` 7, `window` 6,
`add` 7, `bar` 5, `key` 5, `timer` 1) while §5.2's were taken word-wise and did not.

What changed, in the end: state styling **~40 → 0 written**, scrolling **29 → 3**, `elif`/`else` **30 →
9**, `side` **6 → 0**, `tooltip` **3 → 0**, `alpha` **6 → 0 in a screen**, the `text_*` group **~20
properties → 4 tokens, 25 of the 40 uses the `properties` splat**, and every §5.2 row now has
the two numbers it needed rather than one that was neither.

**Every row is a count of *words*, so every row still had to be read by value.** The re-derivation
fixed which bucket a use lands in; it did not fix what the use *is*. Both later items that changed on
a values pass are recorded under "Found during implementation" — item 5, whose 23 uses were centering
alignments, and item 7, whose 26 style-block hits were 25 splats.

## 6. Actions, and the elasticity gap

**67 `action` uses in screen bodies, 21 distinct, plus 6 `value`s.** Their disposition is where Vela's
model and Ren'Py's differ most, and it is not the number of actions that matters — it is their
*shape*.

Vela's actions are a **registry of calls** (`SCREENS.md §7`): `jump`, `call`, `set`, `toggle`,
`play`, `stop`, `open_screen`, `close_screen`, `wait`, `quit`, `quick_save`, `quick_load`. An action
is a word, checked at compile time, dispatched by the runtime.

Ren'Py's actions are **values**. `action i.action` is an object built at runtime and handed to a
widget; `Preference("text speed")` is a value with state behind it; `ShowMenu("save")` is a call
constructed by Python. Three consequences, in order of how much they cost us — all three landed as
item 3:

1. **A screen cannot take an action from its caller.** `choice(items)` gets `i.action` — the menu's
   choices *are* actions supplied as data. Vela's screens could only use the fixed vocabulary, so the
   choice screen was unwritable in principle, not merely untranslated.
   **Landed**: an action is a *value* a screen can pass and a widget can hold.
2. **The registry is too small for an application.** `ShowMenu`, `Preference`, `FilePage`,
   `FileAction`, `FileDelete`, `QuickSave`, `QuickLoad`, `Start`, `MainMenu`, `Quit`, `Rollback`,
   `Skip`, `Return`, `Hide`, `Language`, `Play` — 16 distinct in this project, and most are the
   *host's* business (menus, save files, preferences, rollback), not the story VM's.
   **Landed** as a vocabulary of 26, each entry saying whether the runtime acts on it — and the
   registry is now *read* by the checker, which it was not before item 3: the section claimed
   "checked at compile time" and nothing consulted it.
3. **Some are unimplementable by design.** `Language(("Japanese", "japanese"))` needs a translation
   catalogue (§7); `GamepadCalibrate` needs a gamepad API; `EndReplay` needs replay mode.
   **Named, not dispatched**: each is a host system that wires its own action when it exists, which
   is what `SCREENS.md §7`'s `dispatched` flag records.

## 7. Host systems — the part that is not the language

Seven of the 23 screens are not screens in any interesting sense: they are the *interface to a
system*. `preferences` needs somewhere to keep settings, `save`/`load` need a save system with
slots, pages and thumbnails, `history` needs a log of what was said, `notify` and `skip_indicator`
need transient HUD state, `nvl` needs a second presentation mode, `help` needs the input map.

These are **B**, but they are not *this* milestone's work, and pretending otherwise would be the
mistake this document exists to prevent.

| System | Screens it unlocks | Where it belongs |
| --- | --- | --- |
| **Settings store** — text speed, volumes, skip, fullscreen | `preferences` | **M12.2.** No spec describes one; nothing in the engine keeps a preference. |
| **The screens over the save system** — pages, timestamps, thumbnails, delete | `save`, `load`, `file_slots` | **M12.2.** Slots are real (`M08`, `RUNTIME.md §5`) and the screen over them is not, so this is UI over a system rather than a system. |
| **A log of what was said** | `history` | **M12.2.** Rollback exists (`M08`); the dialogue log is new, and is what `nvl` reads too. |
| **Transient HUD state** | `notify`, `skip_indicator` | **M12.2.** Small, and adjacent to §4's screen work. |
| **The input map** | `help`, `keyboard_help`, `mouse_help`, `gamepad_help`, `about` | **M12.3.** `SCREENS.md §11` has the *model* — semantic actions, per-device profiles — and no map behind it. |
| **Audio playback + Opus importer** | `quick_menu` (mute, volumes) | **M12.3.** `M09` item 1, still open. |
| **A translation catalogue** | `Language(...)` actions, all of `tl/**` | **M12.3.** |

> **Recorded, not discarded.** These are the largest body of work this survey turned up and the least
> like migration — a settings screen is a feature a game written in Vela needs as much as a migrated
> one — so they are the **rest of the M12 series** rather than a footnote here:
> **`M12.2`** for the menu and settings system, the save/load screens over the slots `M08` already
> keeps, the dialogue log, and the HUD; **`M12.3`** for audio, the input map, device variants and the
> translation catalogue. The cut is deliberate: **§4–§6 are the screen *language***, which is what
> "migrate a project's screens" means, and the host systems are what "be a game engine" means. A
> migrated project needs both, and confusing them is how a milestone becomes unbounded.

## 8. What will never migrate

Named so they stop coming up: Ren'Py's compiled output (`.rpyc`, `cache/*.rpyb`), its save files
(`saves/*`, `persistent`), its log, its build metadata (`project.json`, `android.json`, icons), the
GUI skin (`gui/**`), the `gui.*` global mechanism, `Borders`/`Preference`/`StaticValue`'s object
model, `config.*` knobs with no Vela counterpart (`config.console`, `config.has_voice`,
`config.window_icon`), and the look of Ren'Py's default screens.

## Work items

Ordered by what unblocks the most, from the census rather than from taste. **Scope: one at a time,
each finished before the next** — the number is the count in this project that stops being a report
entry when the item lands, and after items 1–4 every one of them is a **screen-body** count (§5.2).

The order was re-derived when the census was, because two consecutive items had been ranked on a
number that was wrong by an order of magnitude. Two judgement calls are worth stating, since they are
not the counts: **`style_prefix` sits above the text-property group** because it is the mechanism that
applies a theme to what a screen draws — 20 uses, every one in a screen body — and **scrolling sits
below `for` and `key`** despite three widgets, because what it unlocks is the *host* screens of §7
rather than a project's own; it stays on the list because each of the three is a whole screen.

**The numbering is stable**: it is how items are referred to in commits and in §5.2, so an item that
turns out to need no work keeps its number and is marked *covered* rather than deleted, and the list
does not renumber under a reader.

2. **Screen composition**: `use screen(args)` and `transclude` (14 + 3). The largest gap, and the

4. **State styling** (0 written in a screen body; 3 in style blocks): a property with a value per

12. **Scrolling**: `viewport`, `vpgrid`, `scrollbar` (**1 + 2 + 0** written, not 29). **Landed** as the

14. **Comparisons and boolean operators in a condition** — *not a row: a prerequisite the rows hid.*

    - **What it produces is checked, not just written**: `vela migrate the_question` now writes

17. **The migrator translates `screens.rpy`.** *Not a row — and the milestone's own exit criterion

    - **What the file is made of.** 1,538 lines: `style` 190 (top level), and inside the 23 screens —

      distinct props.

      `spacer`, `fixed` → `absolute`, `frame`/`window` → `box`, `label` → `text` (Vela's `label` is a

      the block *is* the `vbox`.

      `style_prefix`, the file's `style` declarations (`is` → `from`), and `gui.<x>_color`/`_font` →

      discovered): `xpos 240`, `ypos`, `xsize`, `xfill`, `xanchor` and friends are *reported* per screen,
      as a skin's business. A matched `xalign`/`yalign` pair of fractions lowers to the one of Vela's
      nine anchors it names; a lone axis does not, because `center` is a point and not an axis.

      (animation, `§6`'s not-yet), a `python:` block, a displayable in a style (`Frame("gui/frame.png")`)

      snake case (`Language` → `language`, `Preference` → `preference`, `Skip`, `Rollback`, `FilePage*`,

      a screen cannot share a name in Vela* (`E2003`) while Ren'Py keeps the namespaces apart — and the
      theme's styles are named after the same groups the screens are, so `main_menu`, `notify` and
      `nvl_window` collide the moment the theme and the screens share a module (which they must, because
      styles resolve per file). The fix is a rename in the *merge* (`scripts.rs`), with a report entry,
      like the label/value collision the story pass already handles. And **a bare `action`/`style` prop
      line is not accepted by the parser** even though `apply_prop` implements both (`E5005`): the schema
      a line is checked against and the match that applies it disagree, which is an engine question
      rather than a migrator one.

## Found during implementation

- **`screens.rpy` is not translated by anything, and the exit criterion needs it.** The plan's items are
  all *language* items — the screen language grew conditions, loops, input, state and variants across
  items 6–15 — and item 16 is what finally made the migrator *look* at a `.rpy` file that is not a
  story. Reading its report is what shows the gap: `screens.rpy` is still reported by file, so a
  migrated project gets a theme (`src/gui.vela`) that nothing draws with. "Screens migrate structurally
  and the look comes from a Vela theme" is therefore true of the *language* and not yet of a
  *migration*, and that is item 17.
- **The first liveness count was wrong, and the splat is why.** Counting `gui.` names a screen mentions
  *textually* gives 77 used and 49 dead — but `properties gui.text_properties("name")` never mentions
  `gui.name_xpos`, and it means every one of them. With the splats counted the real split is **118
  live, 8 dead**, and the eight are palette entries (`idle`, `hover`, `selected`, `insensitive`,
  `muted`, `text`) that Ren'Py's own styles read and nothing in a Vela project does yet. A textual count
  is a measurement that looks like evidence and is not.
- **A style paints; it does not place — measured, not assumed.** `size = 40` in a `style` draws bigger
  text; `xpos = 400` and `xalign = 1.0` are accepted and *ignored*. Both were checked by capturing a
  frame through `vela run --capture` and reading it, which is what decided the pass's central rule:
  ~90 of the GUI's placement variables are reported rather than written into a theme, because the file
  they would produce looks migrated and draws in the wrong place. Whether a style *should* carry
  placement is a design question for another day, and the report says so without pretending the answer
  is yes.
- **Linking a style to a theme token by value needs the value to be unambiguous.** The first version
  resolved a colour to whichever variable held the same number, and produced `style interface: color =
  theme.choice_button_text_hover` — alphabetically first, semantically unrelated. `#ffffff` is four
  different roles in the sample's own `gui.rpy`. The rule is now "exactly one holder, or the literal",
  because a literal is never wrong. The test that caught it is `an_ambiguous_colour_is_not_linked`.
- **`SCREENS.md §5`'s own example did not parse, again.** `style body from:` — a `from` with nothing
  after it — is `E1004`, and it had been in the spec since styles landed. Corrected with a
  `**Revised (M12.1).**` note, the same treatment item 7 gave the font example; it is the second time a
  spec example has been the thing that was wrong rather than the code.
- **The descriptor had the field, and had it since M9.** `target.json` has carried `"variants": []` since
  the target drivers landed, with `commands/target.rs` saying it was empty "because there is nothing to
  record: no importer emits a variant". That sentence was reading the word as §3.1's **artifact**
  variant; the *screen* variant — "which platform am I" — is a different thing with the same name, and
  the field was already the right place for it. So item 15's platform half was not new machinery but a
  field that had been waiting, and the doc now separates the two meanings rather than leaving one of them
  to be re-derived by whoever reads it next.
- **Ren'Py's `small` cannot be Vela's `small`.** `renpy/main.py` decides it from the screen's *physical
  diagonal* (`math.hypot(w, h) / dpi`, six inches and up means `medium`), which a desktop build cannot
  measure — Vela has no DPI, and `1200x700` is a laptop window in one context and a tablet in another.
  What Vela *can* measure is the room the frame has, which is what the sample's own use is about ("no
  room" for the side image). It is Vela's number, so §2.6 states it as Vela's rather than presenting it
  as Ren'Py's rule — the difference between a documented choice and a claim that would be wrong.
- **A closed vocabulary makes `tablet` and `touch` errors, which is a migration finding.** Ren'Py answers
  `False` for any name it does not have, so its authors never had to think about whether a name exists;
  Vela checks the name where it is written (`E5018`). No sample screen uses a variant outside the four,
  but a *third-party* project that branches on `touch` or `tablet` will migrate into an error rather
  than into an arm that never draws — which is the right way round, and staged work: the names arrive
  when a target that can answer them does (`android`/`ios`).
- **Adding a question to the language split `E5018`'s home in two.** Item 14 made `check_actions` stop
  visiting conditions, so a call in a condition is checked there no longer — and `variant("pc")` is
  legal in both a condition and a value position (`text variant("small")`). The vocabulary check
  therefore runs from *both* expression walks (`check/conditions.rs` and `check/actions.rs`), which is
  correct because the positions they cover are disjoint, and is written down in both files so the next
  rule that walks expressions knows there are two entry points.
- **`text variant("pc")` drew nothing until `text_of` learned about questions.** The evaluator answered
  the question in a condition and in `value_of`, but a widget's content goes through a third path
  (`text_of`), which sent every call to `String::new()`. Found by testing the claim `value_of`'s own
  comment makes — that a question is a value a screen can draw — rather than by reading the code.
- **Two budgets caught the shape of the change, and both were right.** `eval.rs` went two lines over
  `REPO_LAYOUT.md §3.1`'s 500, and its `Expr` match over the 11-arm dispatch limit — the second because
  the question arrived as a *second* `Call` arm rather than a branch inside the first. Neither was
  allowlisted: the style-resolution family (what a style paints, per state, through its chain) moved to
  `paint.rs`, which is the module that produces a `Paint` and now says so; and the second arm folded back
  into the first (`question_of(expr)?.or_else(action)`), which is one arm per expression kind instead of
  two for `Call`. The lint found a real structural regression, not a formatting nit.
- **Item 15's seven `variant` calls are two questions, and the prerequisite they share was not in the
  plan.** Line 114 asks *how big is this screen* (`small`); lines 317, 322 and 768 ask *which platform
  am I* (`pc`, `web`, `mobile`) — six calls to one, one call to the other. Both sources exist in Vela
  already: the target is recorded per build (`target.json` carries `linux` and `input_profile`, and
  `commands/target.rs` says its variant set is empty because *nothing emits one*), and the window size
  reaches `lay` but nothing tells a condition about it. So item 15 is a vocabulary question with two
  answers, and it is not what the row describes — which is why measuring it first turned up item 14.
- **The screen evaluator answered `false` for every comparison it did not implement, and said nothing.**
  `is`, `is not` and `not` were the whole of it; `Expr::Binary { _ => false }` swallowed `==`, `and` and
  `or` (`LANGUAGE.md §3`'s operators, all of them) with no diagnostic anywhere. Nine of the sample's 31
  screen conditions were therefore decided false: `scroll == "viewport"`, `device == "keyboard"` and the
  three `variant` chains. **One of those nine is item 13's own use** — the help screen picks its tab with
  `device == "keyboard"`, so the item that landed a screen variable shipped a mechanism whose sample use
  could not compare it. They now work, and this is the third time an item's measurement has been the
  thing that found a defect in the item before it (item 10 found the dotted-value parse; item 13 found
  the a11y label; this found the operators).
- **A condition is not an action position, and the checker said it was.** The first run of `W4013`
  reported every call in a condition *twice*: once as `W4013`, and once as `E5012` ("no action called
  `GamepadExists`"), because `check_actions` walked condition expressions as action positions. A
  condition is decided by truthiness rather than read as a value, so a call in one is never an
  action — the walk now visits an `if`'s bodies and not its conditions, which is the same correction the
  value layer already made for `image` and `theme.bg`: the question is *what position is this*, and one
  answer per position. Found by writing the test, not by reading the code.
- **Item 13's three `default` lines are three different things, and the count hid which.** One is
  *module* level (`default quick_menu = True` — already supported, and not a screen's), one holds a
  **host displayable** (`FilePageNameInputValue`, which is §7's save-screen system), and one is real:
  the help screen's `device`, initialized once, written by three buttons, read by its `if` arms. So the
  item is one use of one mechanism rather than two uses of one — and that one is exactly the "screen
  remembers a choice" case, which is why it was worth building rather than deferring.
- **The registry had already named the write, and the name was better than the one this item planned.**
  `set_screen_variable` has been a declared entry since M7 (`dispatched: false`), in Ren'Py's own words.
  The design question — an action of its own rather than an overload of `set` — was settled by that
  entry existing: adding `set_screen` beside it would have been two names for one action, and renaming
  it would have been a vocabulary change nobody asked for. The item *dispatches* what was declared.
- **An action's argument had to become a value, and that is a fix to `open_screen` too.** Arguments were
  strings "as written", which is right for a *name* — `open_screen(settings)` is for the runtime to
  resolve — and a lie for a *value*: `set_screen_variable(device, item.kind)` would have written the
  words `item.kind` into the variable. So `Action::args` is now `Vec<Value>`: a name the screen does not
  have in scope stays a name, and one it does is resolved before the runtime sees it. A screen that
  passes a parameter as a screen name (`open_screen(target)`) now works, where before it opened a screen
  called `target`.
- **A variable is *named* state, and §12's node-state mechanism is still waiting.** `SCREENS.md §12` said
  the reload diff "lands with the first stateful widget". A screen variable is not that: it survives a
  reload by living outside the screen, in the runtime, rather than by being matched to an old node. Said
  in §2.5 and in §12 so the two kinds of state are not conflated — a scroll offset or an input buffer is
  still what the diff waits for.
- **The offset is a value here and state in the other half, and that is why the item splits.** `nvl`'s
  `vpgrid` says *where to look* (`yinitial 1.0` — the bottom, always); `game_menu`'s viewport says *how
  the player looks* (`mousewheel`, `draggable`, `pagekeys`, a draggable `scrollbar`). A value is what a
  screen can carry and a pure function can compute, and it is what `SCREENS.md §2` requires; driving the
  offset is *state*, which no widget has yet — `§12`'s reload diff is explicitly waiting for the first
  one. So the item landed the half the language owns and named the half M12.3 owns, and the row says
  which is which. Had it landed both, the state store would have been designed here by accident.
- **Clipping did not exist, and scrolling is impossible without it.** `vela-render` had no scissor and no
  clip rectangle: a quad was drawn where it was put. A viewport is the first thing that ever needed a
  *window*, so the clip was invented rather than reused — a rectangle on each vertex, intersected on push,
  discarded in the fragment stage. **Per vertex and not per draw call**, because a draw call here is a run
  of quads that share a texture: a scissor would split every run crossing the window's edge and pay a
  state change per split, while a vertex attribute costs four floats and leaves the batching alone.
- **A viewport cannot use `align`.** `align` clamps a child to the slot it is given — on purpose, since a
  container bigger than its content must not let a child hang out of it — and `place` then re-measures the
  child at that clamped size. For a viewport both are exactly wrong: a clamped child is a child with
  nothing to scroll and a squeezed content. So the child is placed at the size it *measured* to, offset by
  the travel, and the clipping is what keeps it from spilling. A reader who wondered why the viewport does
  not use the container helper the others use now has the answer in the code.
- **The two halves of a viewport are invisible in each other's test.** The layout test can see the content
  keep its height and the offset take effect; only the draw list can see the clip, and only a frame can
  show that content beyond the window is not painted. Both are asserted, and the frame was checked by
  capturing one: content 600px tall in a 400px window, the 200px beyond it not drawn, and `initial 0.0`
  against `initial 1.0` showing the top and the bottom.
- **Item 11's row had its premise backwards: `image` drew nothing.** It said *"Vela's `image` takes a
  reference"*, implying the widget worked and only *computed* sources were missing. In fact `image` was a
  registered widget with no `Kind`, so `kind_of` fell through to `Measured { ZERO }`: it laid out at
  nothing, painted nothing (`paint.rs` had no arm for it), and its reference was never checked either —
  `image missing.thing` was accepted and invisible. Everything the row wanted was downstream of that, so
  the item became "make the widget work": a node kind, a size from the platform's table, a texture at
  paint time, and a reference that may be a path or a value. **The lesson is the one items 5, 7–10 keep
  teaching**: the row described a capability by its *symptom*. `add SideImage()` looks like "a computed
  source" until you read what `image` does, and then it is "the widget is inert".
- **`add` is not a widget, and the row's mapping said it was.** `SCREENS.md §5.1`'s row reads `add <expr>`
  → `image <ref>`, which is the *migrator's* translation rather than a Vela name; `add bg.room` is
  `E5005`, "no widget called `add`". Worth stating because the table's other rows are Vela's own names,
  and one that is Ren'Py's reads as an omission from the registry.
- **A picture is two facts from two parties, and the second one arrives late.** The build knows how *big*
  a picture is; only the platform that uploaded it knows which *texture* it became, and that happens when
  a window exists — after screens are compiled. So the table is injected (`ScreenSet::with_images`, like
  the font table) and the joining is a function (`play::images::table`) rather than a few lines in the
  frame loop, which is what makes it testable without a window. A name the platform did not upload is
  *left out* rather than given texture zero, because zero is a real texture and would draw the wrong
  picture confidently.
- **There are two runners, and they have to agree.** `vela run` draws screens in a window; `vela run
  --capture` draws them with no display at all (`frame.rs`). Both lay a screen out, so both need the
  table — a capture that skipped it would be a screenshot of a picture-less interface, and a screenshot is
  exactly what a reviewer checks a screen against. Found by wiring the first one and asking who else
  calls `paint`.
- **`SCREENS.md`'s length was never the defect — the budget that said it was has been removed.** Items
  7–10 added four language sections (§2.2–§2.4, §5's font token) and the file passed the `.md` hard
  limit, which is when the limit turned out to be measuring the wrong thing: a code budget stands for
  how much of one file a reader must hold to change it, and a spec is long because the contract is. So
  `REPO_LAYOUT.md §3` no longer budgets documents and `check-file-size` no longer walks them; prose is
  left to review, where the one-sitting rule is applied by a reader rather than by a line count. The
  compression pass that had squeezed §2.2–§2.4 to fit is reverted where it cost specificity — the spec's
  own convention is to name the test.
- **Item 10's `for` needed a value layer that did not exist, and the row's own count hid it.** The row
  said "children from data" and 6 uses. By value: three of the six iterate a *screen parameter*, one a
  global, and two a `range(...)` **call**; five of the six bodies read a **field** of each element
  (`i.caption`, `i.action`, `d.who`, `d.window_id`). So the gap was not the loop — it was that a screen
  value had no list and no record, and `value_of` could not resolve `Expr::Field` at all. The loop is
  the easy half once an element can be a record with fields; the count said nothing about either.
- **Nothing feeds a screen a list, and the item stops one system short of mattering.** `Screens::dialogue`
  binds two strings; `Stack::open` passes no arguments. So the sample's `choice(items)` — the screen
  this item is *for* — will walk an unbound value and draw nothing until the menu's choices
  (`Command::Menu` carries them) reach a screen. That is §7's host systems and M12.2's, and the row,
  `SCREENS.md §2.4` and this file all say so rather than implying the loop works. Item 3 hit the same
  wall from the other side: an action could be *data* before anything supplied the data.
- **`text option.caption` did not parse, and the sample's menu is written that way.** A bare name in a
  widget's line is ambiguous by design (`at bottom` and `text line` are one shape), and the lookahead
  that resolves it required an operator, a call, or an index after an identifier — a dotted chain did
  not count even though it had already been stepped over. So `option` was read as a prop *name*, and
  `.caption` had nowhere to go: two `E1004`s per menu row. No prop name contains a dot, so the chain
  settles it alone; the rule now says that, and a screen test pins it.
- **A data-driven label is a label the accessibility tree cannot see.** `W4010` fires on the sample's
  `textbutton i.caption` — correctly, and for a reason worth writing down: the a11y tree is built from
  the screen's *source*, and `label_of` accepts only an explicit `label` or a single `text` child whose
  content is a *literal*. `text line`, in every dialogue screen, has the same shape. The lint is honest
  (self-voicing really would announce nothing), so the fix is not to silence it but to derive labels
  from the *evaluated* tree — which is a change to where the tree comes from, not to the lint. Recorded
  in `SCREENS.md §10` as a `**Note.**`; found only because a caption can now be data.
- **Item 9's timer was not "a thin addition", and the row that said so was wrong about its own reason.**
  The row justified the ranking with "`World::clock` exists and is deterministic". It does exist —
  `vela-vm`'s `time.now` reads it, and a save round-trips it — but **nothing ever advances it**:
  `ops.rs` says it is "injected and advanced by explicit ticks", and no caller ticks. Nothing else is a
  clock either: the screen runtime is clock-free by construction (`lay` and `draw` take no time), and
  `vela-host`'s README describes the `Clock` trait `CONVENTIONS.md §2.2` names as "the single registered
  exception for clocks" — a trait that **does not exist in the source**. So the syntax was the thin
  part and the firing is not, and the timer is carried rather than pretended: `Laid::timers` holds the
  deadline and the action, the docs say nothing fires them, and `SCREENS.md §2.3` carries the
  `**Not yet.**`. What the row got right is that the construct is small; what it got wrong is that the
  engine behind it was already there.
- **A screen cannot name a semantic action without the host, and the host is below the checker.** The
  vocabulary a `key` names lives in `vela_host::Action` (rank 1, and it depends on `winit`); the
  checker that has to reject a misspelling lives in `vela-ui` (rank 8). Neither can move: a screen
  checker that pulled a windowing library in to validate a name would be a worse trade than a mirror,
  and the host cannot depend upward. So the names exist twice — `vela_host::Action` and
  `vela_ui::input::SemanticActions` — which is the duplication this repository normally refuses. It is
  made safe where it can be: `crates/vela-cli/src/tests/ui_tests.rs` asserts the two lists agree name
  for name, so a drift fails CI instead of producing a binding the editor accepts and the window never
  delivers. Recorded rather than hidden, because "we mirrored a list and pinned it with a test" is a
  decision a reader should be able to disagree with.
- **`SCREENS.md §11` named an action that has never existed.** The section listed `ui_confirm` among the
  semantic actions; `vela_host::Action` spells it `confirm`. Nothing had ever compared the two, because
  nothing had ever *read* the doc's list — which stopped being true the moment a screen could write
  `key ui_confirm`: the name would now be `E5014` on a name the spec told an author to use. The section
  is corrected and carries a `**Revised (M12.1).**`.
- **Three of the sample's four `key` names have no Vela counterpart.** `game_menu` is `cancel`;
  `save_delete`, `save_page_prev` and `save_page_next` are entries in Ren'Py's keymap that a Vela host
  has no action for. They are not *one* omission — they are the input map §7 already assigns to M12.3,
  which is a milestone-shaped answer rather than a screen-language one. The item landed what the screen
  language owns and the row now names what it does not.
- **The "the migrator already makes it survivable" claim did not survive being tested.** Item 8's row
  and its work item both said `elif`/`else` are sugar the migrator can lower. The obvious lowering is
  `if a:` / `if not a and b:` — and Vela's screen evaluator does not implement `and`: `eval` handles
  `is`/`is not` and negation, and every other binary operator is *false*. So a lowered `elif` would have
  drawn nothing, silently, in exactly the two three-arm chains the sample has. The other lowering —
  `else:` with an `if:` nested inside it — needs the `else` the row was about in the first place. The
  row now says that instead of guessing that a migrator would handle it, and the item landed the
  construct.
- **Item 8's count was 37 / 9, not 39 / 10.** Measured by the §5.2 rule: 28 `if`, 4 `elif`, 5 `else` in
  screen bodies, forming seven chains — five `if`/`else`, one `if`/`elif`, one `if`/`elif`/`else`, one
  `if`/`elif`/`elif`. Not one `if` in a `style` block or outside a screen. The row has carried 39 and
  10 since the re-derivation that was meant to fix exactly this kind of number, which is the point: a
  count is only as good as the pass that took it, and this one was never taken.
- **The arms are clauses, not sibling lines, and that is what the walkers depend on.** `elif`/`else` are
  lines in Ren'Py, so the obvious CST is a sibling `ScreenLine::Else`. Storing them *inside* `If` —
  `IfStmt`'s shape (`LANGUAGE.md §3`) — is what makes a stray `else` unrepresentable and lets the
  builder pick an arm with one call (`arm_of`) instead of a loop that remembers what the line before it
  concluded. The cost is that a walker's `match` arm on `If { body, .. }` still compiles while losing
  the other arms, which no compiler catches: `ScreenLine::arms()` answers "every arm" once, and the
  eleven walks that recurse now go through it.
- **Item 7 was not a group, and half its count was the row below it.** The row said ~20 distinct
  `text_*` properties, 14 in screen bodies and 26 in style blocks. There are **four** distinct tokens
  in the whole file, and the 26 in style blocks are **25 `properties gui.text_properties(…)`** — the
  `properties` splat, which the *same table* calls **C** — plus one `size gui.text_size`, which is the
  `size` prop reading a theme value. So the row's style half was the C mechanism item 4 had already
  found, re-counted. The screen half is 13 `text_font "<literal>"` (all on one screen, so the language
  names render) and one *computed* `text_color` in `history`, a §7 host system. `text_size` is written
  zero times as a text property and `text_align` zero times anywhere. The item is a single capability,
  not a family — the same shape as item 5, and found the same way: by reading the values.
- **The mechanism was a language-surface choice, so it was asked rather than taken.** A font a widget
  names could be a new *prop family* on every node — Ren'Py's "property on a child that does not exist
  yet" — or a `style` setting. The second was chosen and built: `style`'s `font = theme.<token>`
  (`SCREENS.md §5`), reading a theme `font` token the parser already accepted and nothing consulted.
  The prop family was rejected because `textbutton "X"` lower to a `button` with an explicit `text`
  child (`§5.1`), so there *is* no child that does not exist yet, and because §4.2's rule is that text
  appearance comes from `style` — the same answer that makes `color` a setting rather than a prop.
- **`SCREENS.md §5`'s own theme example did not parse.** It read `font body = @"fonts/inter.ttf" size
  22 leading 1.4`; a setting body is `key = value` (`LANGUAGE.md §7`) and there is no trailing-word
  form, `leading` has no reader in `vela-text`, and the path is an asset. The token is now a name and
  the size stays the `size` setting, and the section carries a `**Revised (M12.1).**` note saying so.
- **Item 5 dissolved once its *values* were read, not just its count.** The row said 99, the re-derived
  count said 23 in screen bodies, and what those 23 *are* is 19 centering or edge alignments plus four
  `gui.*` reads — so the item had no work in it. A count of *uses of a construct* is not a count of
  *things Vela cannot express*, and the gap between the two is where three items in a row turned out to
  be smaller than their ranking. The re-derivation in §5.2 fixed the counting; reading the values is
  what fixed the ranking.
- **The census was re-derived after item 4, and it was wrong in more places than one.** Item 4's own
  row claimed ~40 uses of the state prefixes against **0 written in a screen body** — the ~40 are the
  state keys the `properties` splat *injects*, a mechanism the same table calls **C** — and the same
  flaw turned out to hit the rows around it: scrolling was **29** by a text search and is **3** as
  widgets, `elif`/`else` **30** is the whole `if` family (**9** of **37** is the gap), `side` **6 → 0**,
  `tooltip` **3 → 0**. §5.2 now says how the counts were taken and carries a `screen / style` split
  for every property row; §4's and §5.1's tables carry the corrected numbers; and the work list below
  was re-ranked on them. The lesson is in the method, not the arithmetic: counting a *word* counts
  comments, strings, and prose, and a survey whose whole authority is its numbers has to say which
  question each number answers.
- **Item 3 found the action registry was inert.** `SCREENS.md §7` said the action set is a registry
  "checked at compile time", and nothing consulted it: `ActionRegistry` was read only by `vela doc`
  and by hover, so `action quitt()` was accepted and drew a button that did nothing, with no
  diagnostic. The section now describes what is actually true — the checker reports `E5012` for a name
  that is not registered and `E5013` for the wrong count — and each entry carries whether the runtime
  acts on it, because most of the vocabulary is a name before it is a behaviour.
- **Item 2 found a code collision in `SCREENS.md §2`.** The section promised "screen calls must match
  the declared parameter list (`E5004`)", and `E5004` is the *widget* single-child arity rule — it was
  never this check. The real one is `E5010`, and §2 now names it. Worth watching: a code named before
  the check exists, for a check that turns out to be about something else.
- **Item 1 falsified a rule in `LANGUAGE.md §5.4`.** The grammar's single `param` production is shared
  by `fn`, `effect`, lambda, enum-variant payload and `screen`, so making the type optional makes it
  optional for all of them — and "function parameters and return types are always explicit" stopped
  being true. Decided (asked, not assumed): the type is optional everywhere, an absent type is
  `Unknown`, and §5.4 carries a `**Revised (M12.1).**` note rather than a per-construct exception.
  The alternative — the parser accepts an omitted type and the checker reports `E3003` for every
  construct but a `screen` — was rejected as two rules where the language only needs one.

## Still open

- **§7's split is settled**: the host systems are M12.2 and M12.3, in that order, before M13. What
  those steps contain in detail is theirs to define — they have their own documents.
- **What "migrated properly" means for a *skin*.** The decision in §2 is that Vela does not
  reproduce Ren'Py's look. If that is wrong, the 190 styles and 48 images become translation work,
  and the estimate changes by an order of magnitude.
- **`gui.rpy`'s `init python` blocks** (2) hold real logic (`gui.text_properties()` and friends) and
  are not data at all. They are **C** until something needs them.
- **`tl/**`'s 52 files** are a fifth of the project by line count and are entirely unowned.

## Risks

The risk this milestone carries is **scope**: "implement what Ren'Py has" has no natural end. The
mitigation is the census — every work item above carries the number of uses in a real project, and an
item with no uses is **C**. The other risk is the opposite one: implementing so little that a
migrated project is a script with no interface, which is the complaint that started this document.
